## RQ2: 백엔드 특성 — prefill과 decode에서 백엔드 순위가 왜 뒤집히는가?
### NPU의 decode 약점
- TODO: Figure 7
- NPU decode throughput은 생성 토큰 수가 아니라 context size에 의해 결정됨
  - context 16 → 4096: Llama3.2-1B 61.6 → 47.0 tok/s (-23.8%), Qwen2.5-1.5B 43.9 → 35.1 tok/s (-20.0%)
  - 같은 context size에서는 n_gen = 15/63/255 곡선이 거의 겹침
- 원인
  - decode는 step당 토큰 1개만 생성 → 병렬성이 낮고, 계속 커지는 KV cache를 반복해서 읽음 → compute-bound가 아니라 memory-bound → NPU의 peak compute를 활용하지 못함
  - NPU는 shape이 고정된 static graph로 decode를 실행 → 긴 decode를 지원하려고 큰 context size(예: 4096)로 그래프를 미리 잡음 → 실제 context가 짧아도 매 step 비용이 커짐
- (검토) CPU/GPU/NPU가 같은 메인 메모리를 공유하므로 "memory-bound"만으로는 NPU가 CPU보다 느린 이유가 설명되지 않음. 백엔드 간 차이를 만드는 건 static graph per-step overhead와 invocation overhead 쪽
- (검토) Figure 7의 프레임워크가 명시되지 않음. 수치(Llama 1B ~60 tok/s)는 GENIE(~26)보다 MLLM(w4a16, ~62)에 가까움. 또한 Qwen은 context 1024에서 급락 후 2048에서 회복하는 등 단조 감소가 아님

### CPU가 decode throughput 우위

### 정리
- NPU: compute-bound prefill에 최적 / decode에서는 static graph overhead와 낮은 amortization이 병목
- CPU: dispatch overhead가 낮고 cache 활용이 좋아 보통 decode에 최적
- GPU: long decode에서 CPU 부담을 줄이면서 CPU에 근접한 throughput, 경우에 따라 에너지 효율도 더 좋음

### Finding 6: CPU–NPU invocation 파라미터 (inter-backend)
- CPU와 NPU는 독립적으로 동작하며 RPC(Remote Procedure Call)로 통신: CPU가 RPC로 파라미터 전달 → NPU가 연산 실행 → 결과는 비동기로 반환
- TODO: CPU ↔ RPC ↔ NPU 관계 그림 (polling 표현)
- TODO: Figure 9
- RPC polling time
  - 5–65535 µs sweep, GENIE/MLLM 기본값 9999 µs
  - throughput은 거의 무관 (-7.2% ~ +0.1%)
  - 5–20 µs로 줄이면 토큰당 전체 에너지 30.9–37.8% 감소
    - 감소분 대부분이 NPU 에너지(-49.8 ~ -70.8%), CPU 쪽 변화는 작음
  - 논문 해석: 완료 감지가 빨라져 NPU가 불필요하게 active 상태로 머무는 시간이 줄어듦
  - (검토) FastRPC/QNN HTP의 polling time은 "polling 주기"라기보다 interrupt 대기로 넘어가기 전 busy-poll을 유지하는 시간 window로 알고 있음. 그렇다면 값을 줄일수록 busy-wait 자체가 줄어 에너지가 감소하는 것이고, "완료 감지가 빨라져서"라는 논문 설명과는 방향이 다름. NPU 에너지가 크게 줄어든 것도 DSP 측 polling이 함께 줄어든 결과로 보는 게 자연스러움 → QNN HTP perf infrastructure 문서로 확인 필요
- NPU sleep latency
  - 5–65535 µs sweep, GENIE/MLLM 기본값 40 µs (에너지 관점에서 너무 공격적)
  - 에너지 최적점은 1280–65535 µs, 토큰당 에너지 44.6–50.9% 감소
    - NPU 에너지 성분 66.7–100% 감소
  - throughput 손해 없음 (-0.9% ~ +16.2%), Llama decode는 throughput 최적점과 에너지 최적점이 동일
  - (검토) "다음 명령이 없을 때 얼마나 기다렸다가 sleep에 들어갈지"라는 정의는 부정확할 가능성이 높음. Hexagon power API(HAP_power / QNN HTP perf config)의 sleep latency는 "허용 가능한 최대 wake-up latency" 투표값으로, 값이 작으면 얕은 저전력 상태만 허용되고 크면 더 깊은 sleep(power collapse)까지 허용됨 → 큰 값에서 에너지가 줄어드는 결과와 맞음. 논문의 "idle을 더 오래 유지한다"는 설명도 이 관점에서는 부정확
  - (검토) 연산 중인 NPU의 에너지 성분이 100% 감소하는 건 물리적으로 불가 → rail attribution 또는 카운터 해상도 문제 가능성

### Finding 7: Thread–core affinity (intra-backend, 단 GPU/NPU 효율에도 영향)
- TODO: Figure 10 (Qwen2.5-1.5B decode, Xiaomi 17 / Mask = 사용 코어 조합, M: mid, L: large)
- CPU·NPU 백엔드: thread 수와 활성 core 수를 맞춰야 함
  - thread 수 ≈ 활성 core 수일 때 throughput 최고
  - thread 수가 core 수를 넘으면 throughput 급락 → core 선택만이 아니라 thread–core를 함께 설계해야 함
- NPU 백엔드: host 참여를 최소화할수록 좋음
  - CPU thread 수가 가장 적을 때 throughput·에너지 모두 최적
  - host CPU thread는 NPU 연산을 병렬화하지 않음 (NPU 내부 병렬 실행은 HTP 런타임이 별도로 담당) → 추가 thread는 orchestration overhead와 경합만 늘리고, CPU 전력 증가로 SoC 총 에너지가 악화됨
- GPU 백엔드: host 쪽 동시성이 충분하되 과하지 않아야 함
  - thread 수가 활성 core 수를 넘어도 throughput 영향은 제한적이고, 에너지가 오히려 줄기도 함
  - thread가 너무 적으면 dispatch/동기화가 병목이 되어 GPU throughput 크게 저하
- 결론: thread affinity는 CPU 전용 최적화가 아니라 시스템 수준 스케줄링 knob

### Finding 8: 에너지 비친화적인 DVFS (intra- / inter-backend 모두)
- DVFS(Dynamic Voltage and Frequency Scaling): 부하에 따라 프로세서(CPU/GPU/NPU)의 클럭 주파수와 전압을 실시간으로 조절하는 기술
  - 동적 전력 ∝ C·V²·f이고 주파수를 올리려면 전압도 올려야 하므로, 성능 증가폭보다 전력 증가폭이 훨씬 큼
- 기본 DVFS 정책이 에너지 최적이 아닌 이유
  - accelerator 중심 워크로드에서도 host CPU를 과도하게 고주파수로 운용 (overprovisioning)
  - 더 나은 중간 대역 동작점을 놓침
  - prefill/decode의 phase별 특성을 반영하지 않음
- 실험 조건
  - CPU: 두 클러스터 policy0(cpu0–5), policy6(cpu6–7) — vendor DVFS 제약으로 고정·유지 가능한 21개 레벨 조합만 사용
  - GPU: 15개 주파수 레벨
  - NPU: GHz 단위가 아니라 governor 수준의 voltage corner 단계 (disable, min, svs2, svs, svs_plus, nom, nom_plus, turbo, turbo_plus, turbo_l2, turbo_l3, max)
